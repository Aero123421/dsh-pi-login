# 状態の所有と失敗時の復旧

対象はDSH `0.2.1-alpha.2`、Pi SDK `1.1.0`です。接続の設定はHostのSettings、認証情報はHostのCredentialsを正とします。Clientやキャッシュは、それらを操作・表示するためのもので、保存の成功を代替しません。

## 接続とモデルの識別

接続ID、DSHのroute ID、Piのnative service/model IDを分けます。同じサービスの個人用OAuthと会社用キーが、同じ保存先や履歴の認証状態を共有しないためです。通常・Fast・Contributorの表示上の選択IDは、送信先のnative model descriptorと別に管理します。

プロフィールのキーと起動世代、接続の認証世代、送信先とAPIを照合します。プラグイン経由で認証を変更した場合、古い画面、ログイン、一覧取得の結果を新しいアカウントへ反映しません。Clientは開いた時のプロフィールと認証世代を保持し、編集の保存は開いた時のSettings revisionを使います。Hostでも同じ条件を検査します。

`prepareCall`は、そのagent stepの設定を固定します。次のstepは現在のモデル選択を読み直します。履歴のopaque replayはroute・native provider・認証世代・endpoint・APIが一致する場合だけ復元し、それ以外は通常のテキストとtool結果として扱います。

## 認証情報を含む変更

SettingsとCredentialsを一つのトランザクションでは更新できません。そのため、中間状態を保存して利用者が回復できるようにします。

| 操作 | 保存する順序 | 途中失敗した場合 |
| --- | --- | --- |
| APIキーで接続を作成 | オフの接続 → 所有recordへキー保存 → 接続オン | 作成済みの行から認証を保存し直すか、接続を削除する |
| APIキーを交換 | 新recordを回収候補として記録 → キー保存 → 新recordへ交換し旧recordを回収候補へ → 旧record削除 | 現在のキーと未回収recordを区別して表示し、「認証情報の削除を再試行」で回収する |
| 認証方式を変更 | 新しい認証先・オフ状態・旧record回収候補を同時保存 → 旧record削除 | 認証は再設定し、残った旧recordの回収を再試行する |
| 接続を削除 | `deletionPending`・オフ・認証世代更新 → 専用recordと回収候補削除 → 接続の行を削除 | 無効な行を残す。同じDeleteで再試行でき、再起動後も削除待ちを保持する |

回収候補にはrecord IDだけを保存し、キーやOAuth tokenを入れません。他の接続が使用中のrecordは削除しません。同じ接続の認証書込みと削除は並行させず、別の接続の変更は保持します。停止・更新・複製では認証情報を削除しません。

0.7.2以前の失敗で既に孤立したrecordは、所有者を推測して一括削除しません。この仕組みは、0.7.3以降の操作に回収先を記録します。

## Museのアカウント一覧

再認証を開始すると、認証世代の更新と古い保存一覧の削除を一回のSettings変更で行います。新しい認証が保存された後で一覧を消す順序では、途中の保存失敗や再起動で前のアカウントの一覧が復活するためです。

再認証を取消・失敗した場合、以前の認証情報は保持しますが、モデル一覧は再取得が必要です。オフライン中は再取得できません。通常のキー更新や再起動では、この再認証処理を行わず、同じ接続の保存一覧を利用します。

通常版とContributor版の両方を取得し、接続・アカウント・取消状態を確認し、Settingsへの保存が完了してからキャッシュへ公開します。片方の取得失敗や保存失敗を、モデルが消えたという成功結果へ変換しません。同じアカウントの以前の一覧は保持します。契約・使用量・発行キーも、応答と保存の前後で同じアカウントに属することを確認します。

## 拡張と解除

optional integrationが未ロードでも、保存済みの設定は残します。そのownerの検証を必要とする新規・変更操作は拒否し、無関係な接続の編集や削除は続けられます。

bundle-local ownerをイベントで登録する場合は、登録のdisposerをowner側のcontextへ明示的に渡します。Cordisの`emit()`はlistenerの戻り値を返しません。

```js
ctx.emit('dsh-pi-login/register-integration', owner, dispose => {
  ctx.effect(() => dispose)
})
```

これはPiプラグインが有効な時に登録する契約です。ownerは自身のadapter・route・credentials・解除を所有し、Piプラグインはその公開契約だけを利用します。Piプラグイン自体を再ロードした場合、ownerの再登録が必要です。

## 探索と配布

モデル探索で保存済みのキー・ヘッダーを引き継げるのは、保存されたendpointとAPIが一致する場合だけです。別のdraft endpointへ使うキーは明示的に入力し、元の接続のヘッダーを引き継ぎません。資格情報読取りとHTTP応答後にも接続の世代を確認し、redirectは許可しません。

自己更新はRelease候補、配布ファイル検査、DSH managerへの導入委譲、導入版と実行版の照合を分けます。チェックサムだけでなく、tarの全entry・manifest・DSH対応版を検査します。対応する配布形式は通常のfile/directory entryで、リンクやpathを書き換える拡張を含むarchiveは拒否します。他の画面やCLIで導入された版も、実行版と違えば再起動待ちとして表示します。

## 検証の範囲

回帰テストは通信・保存・取消・世代交代・再起動を制御し、例外だけでなく最終的な設定、認証、登録、画面からの復旧を確認します。実DSHへのtgz導入と本物のSettings画面、Pi SDKとローカルHTTP fixtureを併用します。

Museの非公開API、実アカウントの生成・利用枠・課金、各OSの実機はこの検証だけでは確認できません。対応DSH版を変更するときは、公開API・保存形式・導入経路を改めて検証します。

管理者が外部のcredential referenceや保存recordを直接別アカウントへ差し替えた場合、接続の認証世代の変更は自動検出できません。アカウント変更は接続の再認証・キー更新を通して行ってください。
